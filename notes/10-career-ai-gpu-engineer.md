# AI 框架适配工程师 / AI 驱动工程师 岗位分析

## 核心结论

1. **AI 框架适配工程师**：让 PyTorch/vLLM 在自研 GPU 上跑通并跑快，主战场是框架层
2. **AI 驱动工程师**：实现 Runtime/Driver + CUDA 兼容层，是框架层和硬件层之间的粘合剂
3. **两者的上下游关系**：驱动工程师造"地基"，框架适配工程师造"房子"
4. **兼容 CUDA 接口**是降低适配成本的核心策略，接口越像 CUDA，上层软件适配越容易
5. **PyTorch 的底层结构**：CUDA 只是 GPU 计算后端，Autograd（自动求导）是另一个核心，两者都运行在 CPU 端的 C++ 逻辑之上

---

## 一、PyTorch 的核心架构

```
Python API（torch.tensor, nn.Linear, ...）
        ↓
C++ 核心（ATen 张量库 + Autograd 引擎）   ← 全部在 CPU 上运行
        ↓
    ┌──────────────────────────────────┐
    │  计算后端（按硬件自动选择）        │
    │  CUDA kernel  ← NVIDIA GPU      │
    │  ROCm kernel  ← AMD GPU         │
    │  CPU kernel   ← x86/ARM         │
    └──────────────────────────────────┘
        ↓
cuBLAS / cuDNN / NCCL（NVIDIA 官方优化库）
```

**关键认知**：
- CUDA 是 PyTorch 的 GPU 计算后端，但不是全部
- Autograd（自动求导）= 记录计算图 + 反向传播，是纯 C++ 算法，和 GPU 无关
- 内存管理、算子分发、Python 绑定——全部是 C++ 代码，全部在 CPU 上执行
- GPU 只负责"数值计算"那一段，CPU 负责所有调度和管理

### GPU 利用率不足的根本原因

CPU 侧管理工作跟不上时，GPU 会空等。这就是 AI 框架工程师要解决的核心问题之一：**让 CPU 侧管理开销尽量小，让 GPU 永远有活干。**

## 二、两个岗位的详细对比

### 软件栈层次对照

```
用户写的 PyTorch 代码
        ↓
    PyTorch / vLLM
        ↓
  ┌───────────────────────────────────────┐
  │  AI 框架适配工程师 的主战场            │
  │  · 把 PyTorch 算子对接到自研 GPU      │
  │  · torch.compile / 计算图优化         │
  │  · vLLM 推理适配                      │
  └───────────────────────────────────────┘
        ↓
  ┌───────────────────────────────────────┐
  │  AI 驱动工程师 的主战场               │
  │  · Runtime API（类似 CUDA Runtime）   │
  │  · Driver 层（内核态驱动）            │
  │  · CUDA/HIP 生态兼容层               │
  │  · cuBLAS/cuDNN 等高性能库对应实现    │
  └───────────────────────────────────────┘
        ↓
    自研 GPU 硬件
```

### 对比表

| | AI 框架适配工程师 | AI 驱动工程师 |
|---|---|---|
| **工作重心** | PyTorch/vLLM 层 | Runtime/Driver 层 |
| **类比** | 把 App 移植到新系统 | 造新手机的操作系统和驱动 |
| **需要懂** | PyTorch 源码、模型推理优化 | GPU 硬件架构、驱动开发、CUDA Runtime 内部 |
| **偏向** | 软件/框架 | 系统/硬件 |

## 三、CUDA 兼容策略

### 核心逻辑
> 自研 CUDA 接口越接近 NVIDIA CUDA，PyTorch 等软件适配越容易

兼容程度与适配难度的关系：
- **兼容 CUDA API 100%** → PyTorch 代码几乎不用改，直接跑（AMD HIP 的目标）
- **兼容 CUDA API 80%** → 需要改一部分算子实现，工作量可控
- **完全不兼容** → 等于重写 PyTorch，几乎不可能

AMD 把 Wavefront 从 64 改为 32（RDNA 架构），正是为了和 NVIDIA 对齐，降低迁移门槛。

### 国内厂商策略对比

| 厂商 | 策略 | 代价 |
|---|---|---|
| 砺算科技 | 兼容 CUDA/HIP 接口，专设编译器团队 | 需要维护兼容层，但生态迁移成本低 |
| 华为昇腾 | 自研 CANN 接口（不完全兼容 CUDA）| 每个框架要专门适配，生态建设难度极大 |
| 沐曦 / 摩尔线程 | 高度兼容 CUDA | 降低迁移门槛，快速吸引用户 |

## 五、AI 框架适配工程师的三个工作层次

### 第一层：跑起来（适配）
- 实现兼容 CUDA 接口的适配层
- 把 PyTorch 里所有 CUDA kernel 替换成自研 GPU 的实现
- 让 `tensor.to("自研GPU")` 能正常工作

### 第二层：跑得快（性能优化）
- 分析矩阵乘、Attention、Softmax 等瓶颈算子
- 针对自研 GPU 硬件特性重写 kernel
- 用 torch.compile 做算子融合，减少 CPU 调度开销
- 用 profiling 工具找出 GPU 利用率低的原因

### 第三层：跑大模型（vLLM 适配）
- 适配 PagedAttention、FlashAttention 等核心算子
- 适配 KV Cache 显存管理策略
- 保证大批量推理的吞吐量和延迟达标

## ❓ Q&A

**Q：AI 驱动工程师是不是要实现一个 CUDA？**  
A：更准确的说法是：实现一个**兼容 CUDA API 的接口层**（让 CUDA 代码不改就能跑），同时负责 Runtime 和 Driver 层。真正"造编译器"的工作由专门的编译器团队承担。

**Q：自研 CUDA 跟 CUDA 越接近，PyTorch 适配越容易吗？**  
A：对。这是业界共识，也是 AMD 选择做 HIP 而不是另起炉灶的原因。兼容 CUDA 是降低迁移成本的策略，但真正的竞争力在于：在兼容接口的前提下，针对自家硬件做超越 NVIDIA 的优化。

**Q：PyTorch 的管理层（Autograd/内存管理/算子分发）都是 C++ 在 CPU 上跑的吗？**  
A：对，完全正确。GPU 只负责数值计算那一段，其余所有逻辑都在 CPU 的 C++ 里跑。
